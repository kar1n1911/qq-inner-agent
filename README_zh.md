# QQ Inner Agent（QQ 内部思维智能体）

> **简体中文** | [English](README.md)

一个面向单个 QQ 账号的持久化对话智能体，通过 NapCat 或 SnowLuma 的正向 OneBot v11 WebSocket 接入。每个被启用的群聊和私聊联系人都有各自独立的上下文、记忆与候选发言池。默认预置 DeepSeek；同时支持 OpenAI 兼容的 Chat Completions 与 Anthropic 兼容的 Messages 端点。

## 概述

- 一个 QQ 账号，显式启用需要参与的群聊与私聊联系人。
- 首次参与群聊前有一段观察期，之后由模型选择初始发言风格。
- 候选生成、评估、发送概率与回复预期。
- 群聊与个人相互隔离的长期笔记本、短期细节和特质。
- 支持中文/英文的 Web 控制台，可实时配置、查看日志与 QQ 诊断。
- 预置 DeepSeek，并提供 OpenAI/Anthropic 兼容的 API 适配器。

## 快速开始

### 环境要求

- Linux，Node.js 22.13+；若其可执行文件不在 PATH 中，请设置 `AGENT_NODE`。本 agent 没有任何 npm 依赖。
- Python 3，用于 setup 与安装服务的命令；后台运行依赖 systemd 用户服务。
- 一个已通过 NapCat 或 SnowLuma 登录的 QQ 账号，并开启正向 OneBot v11 WebSocket 服务。参见[桥接连接](#桥接连接)。
- 一个 DeepSeek 或兼容供应商的 API key，以及你想要启用的群/私聊联系人 ID。

本 agent 不需要提权。请把凭据保存在本地 setup 或控制台中，不要放进仓库。

### 配置与启动

在终端中：

```bash
cd qq-inner-agent
./agent setup          # 输入 API key（终端不回显）；选择聊天 ID
./agent contacts       # 保存桥接设置后列出可选 ID；再次运行 setup 可更改选择
./agent check --api    # 校验 QQ 并发送一次小模型请求；不会发送 QQ 消息
./agent install-service
./agent status
```

用 `./agent install-service` 安装后台服务。setup 在保存更改后会重启已安装的服务。在尚未输入 key 和聊天 ID 之前，运行中的 agent 会持续尝试连接 QQ 桥，但不会调用模型，也不会发送 QQ 消息。启用某个聊天后，其新消息才会交给已配置的模型供应商处理。入群观察步骤可能会抓取一段有界的历史样本用于初始分析；它不会把该样本当作新消息重放。

QQ 必须已通过所选桥登录，且其 OneBot WebSocket 服务正在运行。当这两者恢复后 agent 会重新连接；它无法自行登录 QQ 或修复桥。

## 桥接连接

两种桥使用相同的正向 OneBot v11 WebSocket 适配器。同一时间只配置一种桥。

### NapCat

1. 启动 NapCat 并登录 QQ。在 NapCat WebUI 中打开**网络配置 → 新建 → WebSocket 服务器**（正向 WebSocket）。agent 作为客户端连接；不支持反向 WebSocket 与纯 HTTP 端点。
2. 在端口 `3001` 上启用该服务，**消息格式设为 `array`**，设置非空 access token；当两个程序直接运行在同一主机时 host 填 `127.0.0.1`。保持事件推送开启。等价的服务器条目见 [examples/napcat-websocket-server.json](examples/napcat-websocket-server.json)；把它加入 NapCat 的 `network.websocketServers` 列表，并替换其中的 token 占位符。它只是一个服务器条目，不是完整的 NapCat 配置。
3. 运行 `./agent setup`，输入 `ws://127.0.0.1:3001/`、相同的 OneBot token，以及可选的 QQ 账号 ID。控制台中留空账号 ID（或在向导中输入 `-`）表示自动检测已登录账号。也可以稍后在控制台的**配置 → NapCat / SnowLuma**中修改这些项。加载联系人之前请先保存。
4. 运行 `./agent check` 校验桥，运行 `./agent contacts` 列出可用 ID。在开始参与之前，选择聊天并输入模型 API key。

若 NapCat 运行在 Docker 中、agent 在宿主机上，请**在容器内**把 WebSocket 服务器绑定到 `0.0.0.0`，并发布 `127.0.0.1:3001:3001`。agent 仍然连接 `ws://127.0.0.1:3001/`。若在另一台机器上，请使用 TLS WebSocket 代理（`wss://`）或 SSH 隧道映射到本地端口。明文 `ws://` 仅在 localhost 下被接受。端口 `3000` 通常是 HTTP，且 NapCat 的 WebUI 端口不是 OneBot WebSocket 端点。

请使用根 WebSocket 路径 `/`，它同时承载动作与事件；NapCat 的 `/api` 路径不投递事件。`array` 与 CQ 字符串两种消息事件格式都被接受；发出的消息始终使用文本段。自身消息上报会被忽略。若 NapCat 与 SnowLuma 同时运行，需要各自使用不同端口；agent 一次只配置一种桥。

兼容性依据 NapCat 的[网络文档](https://doc.napneko.icu/onebot/network)、[配置 schema](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/config/config.ts)与 [WebSocket 实现](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/network/websocket-server.ts)。自动化 mock 测试覆盖了鉴权、登录/状态、联系人、@提及、私聊回复、自身消息过滤以及两种事件格式。尚未使用真实 NapCat 账号做过端到端验证。

### SnowLuma

登录 QQ，在 SnowLuma 中加载其进程，并启用正向 OneBot WebSocket 服务器。在 `./agent setup` 或**配置 → NapCat / SnowLuma**中输入其 URL 和 access token，然后运行 `./agent check`。请使用桥实际配置的端口，不要假定它与 NapCat 的示例端口一致。agent 无法修复桥自身的 QQ 登录或组件加载故障。

## Web 控制台

### 安装与打开

```sh
./agent install-dashboard   # 生成证书并安装/刷新用户服务
./agent dashboard-key       # 在本地显示私有登录密钥
```

用 `systemctl --user status qq-inner-dashboard.service` 查看控制台服务状态，用 `systemctl --user restart qq-inner-dashboard.service` 重启它。若想改为在前台运行控制台，请先停止其服务，再运行 `./agent dashboard`。

`dashboard.json` 包含绑定地址、允许的来源（origin）和 TLS 路径。控制台服务端的改动需要重启控制台才能生效。agent 的行为设置则支持热重载。密钥/配置的保存使用恢复日志（recovery journal），因此当控制台重启时，被中断的两文件写入可以回滚。

### 访问与配置

安装好的控制台独立于 agent 运行：

- 本机：http://localhost:5097
- 局域网：`https://<主机局域网 IP>:5098`
- VPN：`https://<主机 VPN IP>:5098`

在远程设备上，打开 HTTPS 地址前，需要先把公开的 `dashboard-ca.crt` 导入其受信任的证书颁发机构。请把 `data/dashboard-ca.key` 及所有其他私钥保留在本机。证书覆盖安装时可用的地址；若地址发生变化，请再次运行 `./agent install-dashboard`。远程连通性仍取决于你的局域网/VPN 路由与防火墙。HTTP 监听器仅绑定回环地址。对控制台端口发起的明文 `http://` 请求会被重定向到同一地址的 HTTPS，因此远程设备只需能访问 TLS 监听器。

在本机用 `./agent dashboard-key` 获取登录密钥。会话在 12 小时后过期。HTTPS、HttpOnly Cookie、CSRF 校验、来源白名单与登录限流共同保护远程访问。请勿把这个私有管理服务暴露到公网。控制台密钥可访问配置、保留的对话想法、运行日志以及 agent 控制项。

在**配置**中，输入你的 DeepSeek key，选择 API 格式/模型，并启用所需的群/私聊 ID。**加载 QQ 联系人**可以从已登录的 QQ 账号填充选择列表。API key 在保存后会保持空白显示；界面只表明是否已配置 key。选择**保存并应用**以重载 agent。当配置失效时，正在进行的生成会被取消；已存储的记忆保持不变。应用会在已保存的修订被应用后给出提示。更换供应商主机会要求提供替换 key，或显式清除旧 key。

**概览**显示服务、QQ 与模型状态、就绪情况以及最近的决策。**活动与日志**显示保留的候选发言，并每两秒刷新一次运行日志。**测试 API 连接**会用已保存的供应商 key 发起一次小请求，并计入配置的 API 预算；它不会发送 QQ 消息。启动、停止与重启仅控制 agent 服务，不影响控制台可用性。

### QQ 收发诊断

概览页面包含两个 QQ 诊断，独立于模型和聊天白名单：

- **发送自检消息**会向桥的登录 API 返回的 QQ 账号发送一条带唯一标记的文本消息。成功返回只表示桥接受了该动作；请在 QQ 的自身聊天中确认实际送达。收件人与消息内容不可覆盖。失败或不确定的发送不会自动重试。
- **开始接收测试**会监听 60 秒。请用同一个 QQ 账号向自己或另一个聊天发送若干消息（文本、图片、语音、文件、回复）。请先在桥的 WebSocket 服务器上启用 **reportSelfMessage**；某些桥即使发送成功也不会发出自身聊天事件。查看器仅在账号与发送者都与已登录账号一致时接受 `message` 和 `message_sent` 事件。它会显示最近 30 条事件、文本预览与消息段类型；不会抓取附件、不会调用 AI，也不会把捕获内容写入磁盘。**停止接收**会提前关闭诊断连接。开始新测试会清除上一次的捕获。

若接收始终为空，请检查自身消息上报是否开启，以及 URL 是否承载事件（使用 `/`，而不是 `/api`）。空的捕获不等于接收测试成功。诊断使用已保存的连接设置，因此请先保存 URL/token 的更改。它们可以在 agent 服务停止时运行。

## 配置

### 供应商与模型

向导提供 `deepseek-openai`、`deepseek-anthropic` 和 `custom` 三个选项。当前 DeepSeek 预设使用 `deepseek-flash`；你也可以填入 API 账号可用的其他模型。两个 DeepSeek 配置档共用同一个 API key。

| 配置档 | API 基址 | 请求格式 |
| --- | --- | --- |
| DeepSeek OpenAI | `https://api.deepseek.com` | `POST /chat/completions`，bearer 鉴权 |
| DeepSeek Anthropic | `https://api.deepseek.com/anthropic` | `POST /v1/messages`，`x-api-key` 与 `anthropic-version` |
| OpenAI 兼容 | 你的基址，通常以 `/v1` 结尾 | 相对基址的 `POST /chat/completions` |
| Anthropic 兼容 | 你的基址 | 追加 `/v1/messages`，若基址以 `/v1` 结尾则追加 `/messages` |

也接受以 `/chat/completions` 或 `/messages` 结尾的完整端点。`provider.tokenParameter` 用于选择 `max_tokens`（DeepSeek/较旧的网关）或 `max_completion_tokens`（OpenAI）。`provider.anthropicAuth` 支持 `x-api-key` 或 `bearer`；对于需要 workspace 的 Anthropic key，可使用 `workspaceId`。DeepSeek 预设会禁用扩展思考（extended thinking），以保持短小的结构化阶段响应迅速。应用只读取最终文本，不读取供应商的推理字段。

适配器遵循 [OpenAI Chat Completions 参考](https://developers.openai.com/api/reference/python/resources/chat/subresources/completions/methods/create)、[Anthropic Messages 指南](https://platform.claude.com/docs/en/build-with-claude/working-with-messages)和 [DeepSeek API 文档](https://api-docs.deepseek.com/)。模型的可用性与网关对参数的支持取决于供应商。

在**选择模型**中，保存好供应商 URL、API 格式和 key 后，点击**加载可用模型**。可以选择返回的 ID，或在**模型与 API**中手动输入，然后**保存并应用**。列出模型不会产生一次补全。列表使用供应商返回的第一页（最多 500 个 ID）；没有模型列表 API 的网关，以及未出现在该页的模型，都可以手动输入。DeepSeek 在两种 API 格式下都使用其[模型列表端点](https://api-docs.deepseek.com/api/list-models/)；Anthropic 兼容供应商使用其 [Messages API 模型列表路由](https://platform.claude.com/docs/en/api/models)。

### 语言设置

控制台默认使用简体中文。页面顶部和“配置 → 语言设置”可切换 **简体中文 / English**；登录前的选择保存在当前浏览器，登录后使用已保存的界面语言。登录后点击“保存并应用”可保存界面和回复语言。回复语言可选 **跟随聊天语言、简体中文、English**，与界面语言相互独立。

候选生成、评分和最终发言的系统提示词均使用中文；切换英文界面不会把提示词改成英文。JSON 字段名、协议标识、模型 ID 和原始日志保持不变。默认角色说明也改为中文，升级时仅替换原版英文默认角色说明，自定义角色设定保持原样。

控制台默认使用简体中文，并提供英文选项。请在“配置 → 语言设置”中保存界面与回复语言偏好。无论界面语言为何，系统提示词都保持中文。回复可以跟随对话语言，也可以固定为中文或英文。已有的自定义角色和对话内容不会被翻译。

### 活跃与静默时间

在**配置 → 活跃与静默时间**中，启用每日时间表，选择**活跃起始**、**静默起始**以及 IANA 时区（例如 `Europe/Stockholm`）。活跃区间包含起始时刻、不包含结束时刻。像 22:00–06:00 这样的跨夜窗口同样可用。禁用时间表即为全天可用；起始与结束时刻相同会被拒绝。在下方「连续活跃与休息节奏」被禁用时，处于静默期的 agent 会跳过收到的消息，并暂停所有自动回复，包括 @提及和私聊消息。队列中的工作在截止点被丢弃，静默时段开始后正在生成的回复也无法发出。连接与手动诊断仍然可用。静默时段（quiet hours）是另一项独立限制，用于在活跃时段内抑制主动回复。

### 连续活跃与休息节奏

**配置 → 连续活跃与休息节奏**以概率化的可用性取代严格的每日时间表闸门。默认关闭，以保持既有时间表的行为。所有聊天共享同一个账号级的活跃/休息块，包括直接的 @提及和私聊回复。状态与到期时间持久化在 SQLite 中；轮询、消息和重启都不会对未到期的块重新抽样。时长在配置范围内均匀抽样。相邻的块可以选择相同状态，因此不间断的连续运行可能超过单个块的最大时长。

| 设置（`agent.rhythm.*`） | 默认值 | 含义 |
| --- | --- | --- |
| `dayProbability` | 0.85 | 在活跃窗口内选择活跃块的概率 |
| `edgeProbability` | 0.65 | 静默窗口两端处选择活跃块的概率 |
| `centerProbability` | 0.02 | 静默窗口正中间选择活跃块的概率 |
| `sigma` | 0.22 | 相对整个静默区间宽度的高斯宽度 |
| `activeMinSeconds` / `activeMaxSeconds` | 300 / 1200 | 活跃块持续 5–20 分钟 |
| `restMinSeconds` / `restMaxSeconds` | 600 / 2400 | 休息块持续 10–40 分钟 |

在静默时段内，设 `x` 为按时间表本地时间在该区间内的进度（0 到 1，跨午夜时回绕）。令 `g(x) = exp(-0.5 × ((x − 0.5) / sigma)²)`，则活跃概率为 `edge − (edge − center) × (g(x) − g(0)) / (1 − g(0))`。这是一条有界的高斯形**静默**曲线：休息在正中间最可能发生，活跃概率向两端升高。它是启发式规则，并非对真实人类行为的实测建模。这些是「选择某个块」的概率，不是单条消息的发送率，也不是活跃时间占时钟时间的比例；不同的活跃/休息时长会影响该比例。

块的状态会跨每日时间表边界保持，时长使用绝对经过秒数。时区/夏令时变化只影响下一次抽样所用的本地时间曲线。经过长时间离线后，agent 在恢复时只抽样一个新的块，而不是补算错过的块。编辑节奏或时间表设置会开启一个新的块；无关的设置变更会保留当前块。禁用每日时间表后全天使用 `dayProbability`。禁用节奏则恢复原先的严格时间表。

休息会跳过收到的消息并丢弃排队的回复。若某次回复的生成跨越了块边界，即使下一个块是活跃的，该回复也会被扣留。进入活跃状态不会触发问候，也不会补发错过的消息。处于活跃状态时，观察期、静默时段、预测、逐消息发送概率、冷却与预算仍然生效。因此即使在随机活跃的夜间块中，静默时段也可能抑制主动消息。概览页面会显示当前状态、下一次抽样时间、抽样到的概率以及当前曲线概率。这不需要额外的模型请求。

### 参与限制与热更新

使用控制台实时保存并应用设置，或在本地编辑 `config.json`。agent 每秒检查一次变更；无效的编辑会让上一份配置继续运行。[`config.example.json`](config.example.json) 提供了起始配置；[`src/config.mjs`](src/config.mjs) 定义了完整的默认值与校验规则。

| 设置 | 默认值 | 作用 |
| --- | --- | --- |
| `agent.proactive` | `true` | 在已启用的聊天中考虑非受邀发言 |
| `agent.threshold` | `4.09` / 5 | 开放轮次所需的动机分数 |
| `agent.interruptThreshold` | `4.8` / 5 | 当话题正指向他人时所需的动机分数 |
| `agent.system1Probability` | `0` | 可选的低动机简短回应的触发概率 |
| `agent.proactiveCooldownSeconds` | `180` | 两次主动发言之间的最短间隔 |
| `agent.maxProactivePerHour` | `6` | 每个聊天的主动发言上限 |
| `agent.maxMessagesPerHour` | `30` | 每个聊天的总输出上限，含回复 |
| `agent.pauseSeconds` | `45` | 人类活动后触发一次停顿的秒数 |
| `agent.activeWindowSeconds` | `900` | 超过此窗口后不再唤醒已不活跃的聊天 |
| `agent.quietHours` | `23:00–08:00`，Europe/Stockholm | 抑制非受邀发言；设为 `null` 可禁用 |
| `agent.dryRun` | `false` | 只评估并记录决策，不发送 |
| `provider.requestsPerHour` | `120` | 全局滚动 API 调用上限，含重试 |

已启用私聊联系人中的直接消息、显式的 QQ @提及，以及别名后跟 `:`/`：` 都会指向 agent。直接回复会绕过主动发言冷却与静默时段，但不会绕过总消息/API 预算。由模型推断出的邀约不能绕过这些保护。其他机器人账号可以列入 `agent.ignoredUsers`。

## 对话行为

### 入群观察期

观察期对白名单中的群默认启用，包括本次升级前已启用的群。它在 agent 首次登记该群时开始，或在收到新的自身账号 `group_increase` 入群通知后重新开始。重复的入群通知不会让它重启两次。状态与所选风格在 agent 重启后依然保留。私聊绕过这道闸门。

在群内首次回复（包括 @提及）之前，默认同时要求 **300 秒经过时间与 20 条不重复的人类新消息**。**配置 → 入群观察期**可以修改这些阈值、选择「同时满足/满足其一」，或禁用观察。时间是从登记起算的墙上时钟时间；既有的活跃时间表仍然决定哪些收到的消息会被处理。历史样本、自身回声、重放事件、被忽略用户和无关聊天都不计入。若群内一直安静，观察可能无限期等待足够的新消息。越过阈值绝不会强制问候；通常的活跃窗口与发送策略仍然生效。

agent 会通过当前 OneBot 连接请求 `get_group_info`、`_get_group_notice` 和 `get_group_msg_history`。这些列在 [NapCat 的 API 兼容文档](https://doc.napneko.icu/develop/api)中；其他桥可能不实现这些扩展端点。采集器对群元数据、最多五条文本公告以及一段可配置的历史样本（默认 30）做有界限制。不受支持/失败/格式错误的来源会被记录为不可用，而不是被伪造；可用的实时聊天仍可支撑一个保守的初始风格。不会抓取图片和文件 URL。历史样本仅用于分析，不会重放进发送引擎，也不计入阈值。采集到的历史/公告会在配置的原始数据保留窗口之后被删除，而所选风格会保留。

一旦越过阈值，会发起一次独立的中文 `ORIENT` 请求，分析所提供的群上下文，并选择一个初始发言风格、一段简短概述和若干话题。它使用既有的供应商/API 预算。输出无效或供应商失败会保持闸门关闭，并在 60 秒后重试。必须先成功完成分析，才能进入形成/评估/表达阶段；这些阶段都会收到所选风格作为参考上下文。这会为每次成功的初始定向增加一个模型请求，外加任何失败的尝试；后续的对话学习可以继续改进风格。群元数据与公告始终是**不可信的引用内容**。

**活动与日志 → 入群观察期**会显示经过时间、消息计数、来源可用性以及所选风格。元数据采集在第一个符合条件的群处理周期开始时进行。自动化验证期间未进行过真实的 QQ 历史抓取或模型分析。

### 发送策略与预测

在**配置 → 发送策略与预测**中配置新的发送检查；它默认启用。既有的时间表、静默时段、冷却与速率限制仍然生效。被选中的候选在表达之前会收到一次中文 `FORECAST` 请求：是否发送、正常回复/沉默/负面反应的概率，以及一段简短的回复计划。无效的预测会失败即关闭（fail closed）。这会为一个符合条件的周期增加一个模型请求（一个成功的完整周期共四个请求），并计入既有的 API 预算。

主动发言的准入概率是以下各因子的乘积：

- 基础概率（默认 0.8）。
- 沉淀因子：`min(1, 距最近一次人类消息到达的秒数 / 15)`。
- 恢复因子：`min(1, 距上一次被策略计入的投递尝试的秒数 / 300)`；若无则为 1。
- 节奏因子：`1 / (1 + 最近一分钟内人类消息数 / 6)`。
- 动机因子：`0.25 + 0.75 × (调整后分数 − 1) / 4`。
- 预测因子：`1 − 预测的负面反应概率`。

时间除数、节奏除数与基础概率均可配置。计时在预测请求之前抽样，因此模型延迟不会抬高发言概率。直接请求使用其独立的基础概率（默认 1），不经过上述折减。当预测表示应当等待，或负面反应概率超过其配置上限（默认 0.4）时，两种模式都会被否决。概率抽样对每条触发的人类消息只持久化一次：被拒绝的尝试不会在沉默计时器上或重启后重新抽样。禁用此检查会恢复此前的选择流程。

表达会使用回复计划。只有确认发送后才会建立一个预期，默认按聊天保留 300 秒。下一轮会收到该预测，外加经过的时间以及是否有新的人类消息到达；仅仅到达并不能证明对方回复或同意。预期不会安排自动跟进。**活动与日志 → 发送预测**显示概率、抽样结果、计时因子、结果预测、计划与投递状态。这些预测是主观估计，不是经过校准的概率，也不是对论文实验的复现。

### 自适应角色与记忆

默认中文角色现在强调接住对话线索、轻松的联想与幽默，并开启相关且易于回答的话题，而不是不停地提问或强行活跃。与旧版完全一致的默认角色会自动迁移；自定义角色保持不变。

实际生效的提示词由你可编辑的角色设定，加上按范围划分的笔记本与特质组合而成。键为 `(chat, subject, layer, topic)`：在群聊中，subject 为 `group` 和 `person:QQ_ID`；在私聊中只允许联系人的 `person:QQ_ID`。同一个人在两个群中以及在私聊中的记录是彼此独立的。只有当前群和最近一位人类发言者的笔记本会进入生成。共享的群短期上下文仍然包含其他成员的带署名消息；这些不能与当前发言者的特质混为一谈。保留的候选想法也按发言者分区，以防个人上下文通过该缓存泄漏。

| 层 | 内容与更新 | 每个 subject 的默认值 |
| --- | --- | --- |
| 长期笔记本 | 以话题为键，概括过往事件、约定和持续中的线索。保留未改动的话题，upsert 已有键以修订，显式遗忘过时话题。 | 1,800 字符，最多 24 个话题，自更新起 365 天 |
| 短期细节 | 带署名的原始人类消息，无需模型调用即自动记录。群视图与个人视图在检索时去重。 | 40 条，每条 1,000 字符，72 小时 |
| 特质 | 稳定的兴趣、表达习惯、互动风格与群内主题。与事件历史分开更新。 | 900 字符，最多 24 个话题，自更新起 180 天 |

长期存储借鉴了 [Mamba 的选择性状态空间](https://arxiv.org/abs/2312.00752)中「依赖输入的筛选与循环状态」的思想，此处实现为一个有界的应用层笔记本，**并非 Mamba 神经网络，也不是对其 SSM 的数学复现**。模型在 `FORM` 中最多提出四个话题补丁；未改动的话题保持不变。在容量压力下，重要性更高的条目优先保留，最近更新的条目作为并列时的裁决依据。修订、来源 ID、作者与时间戳都保持可检查。长期与特质的过期独立于原始聊天日志的保留期；所有状态持久化在 SQLite 中。默认每个聊天最多保留 200 个人，满了以后淘汰最近最少更新的个人范围。

**配置 → 自适应角色与记忆**控制这些上限与学习节奏（默认：8 条新人类消息且 300 秒）。同一次 `FORM` 调用分析当前群/当前发言者；它不会为每一位过去的成员单独做一次反思。个人更新必须只引用该人在当前聊天中的真实消息。群更新要求至少来自两位不同成员的消息。这校验的是署名归属，而不是事实真伪或共识。模型被指示要保留分歧，绝不根据一个人推断整个群的偏好。作者、范围、层、来源错误或格式错误的补丁会导致整批更新被拒绝。不需要额外的 API 请求，尽管结构化输出会消耗 token。

有界的「当前群/当前发言者」笔记本与特质会被直接提供，因此过往上下文不依赖关键词匹配。短期 RAG 使用最近三条人类消息，通过词汇重叠（包括中文字符对）、时效性和 owner 笔记偏好，对允许范围内的细节以及最多 50 条 owner 笔记进行排序。默认返回最多 6 条相关细节，排除已在提示历史中的消息。每个阶段都会收到 subject/时间/来源元数据。不需要 embedding API 或向量数据库；关键词检索可能漏掉改述。

**活动与日志 → 学到的聊天风格与记忆**最多显示 200 条，优先显示笔记本/特质，并按聊天、subject 和层分隔。重置只清除该 subject 的三层，保留原始聊天历史和其他 subject；进行中的学习会被作废。新消息可以再次训练它。禁用学习会停止三层的采集、更新与使用；当前对话上下文和 owner 笔记仍然可用。调低上限会在热重载时生效。更长的保留期设置适用于未来的更新，而不会复活已过期的数据。

升级说明：此前未分范围的 `learned_memories` 和 `chat_learning.style` 会作为遗留记录保留在本地，但不会加载进这条新管线。它们不会被自动归属给某个人或某个群。旧的 `learning.maxMemories` 与 `learning.memoryDays` 设置仍为向后兼容而接受；新的分层上限使用 `agent.memory.*`。发送概率、冷却、静默时段与活跃时间表继续生效。

### 请求流程与能力边界

一个周期在候选选择弃权时通常使用两个 API 请求，在发送预测或概率检查弃权时使用三个，在发送时使用四个。禁用发送策略会移除预测请求。突发消息会被合并；最多两个聊天并发运行。若生成期间有新输入到达，过期回复会被丢弃，并处理最新上下文。不确定的投递结果会被记录，且绝不自动重发，宁可偶尔漏发也不重复发帖。

支持文本与 @提及。图片、音频、文件和转发消息的内容以附件标记表示，不会下载或解读。agent 没有 shell、浏览器、文件访问或其他动作工具。它能对话，但不能执行通用任务。

## 运行与本地数据

### 日常命令

| 命令 | 用途 |
| --- | --- |
| `./agent setup` | 配置供应商、key、所选聊天、名称、角色与预览模式 |
| `./agent contacts` | 在本地列出可用的群和好友 ID |
| `./agent status` | 服务状态与最近的连接状态 |
| `./agent logs` | 跟踪运行日志；不含消息正文与 API key |
| `./agent stop` | 停止自动参与 |
| `./agent restart` | 重载配置并重启 |
| `./agent start` | 在前台运行；拒绝第二个实例 |
| `./agent check --api` | 鉴权并发送一次小模型测试请求 |
| `./agent test` | 使用本地 mock 供应商与 OneBot 运行离线测试 |
| `./agent add-memory group:123 "The club meets on Sundays."` | 为恰好该聊天添加一条 owner 撰写的笔记 |

私聊记忆使用 `private:123` 而不是 `group:123`。只有被选中的聊天会被处理。要启用更多聊天，请重新运行 setup，或编辑 `config.json` 后重启。在 setup 中输入 `-` 可以清空列表。移除某个聊天会停止后续处理；已存储的本地历史会保留到保留期结束。

`qq-inner-agent.service` 用户服务会在崩溃后重启。WebSocket 心跳每 30 秒检查一次 QQ；失败的连接会以指数退避加抖动的策略重试。HTTP 请求复用连接池、设有截止时间，并对瞬时故障重试。对话状态存储在本地，而不是依赖模型服务器记住会话。程序不会发送付费的保活模型请求。

`loginctl show-user "$USER" -p Linger` 可显示用户服务能否在注销后继续存活。如有需要，可用 `loginctl enable-linger "$USER"` 启用。这不会让桌面 QQ 会话在注销或挂起后存活：请保持计算机唤醒，并让 QQ/SnowLuma 持续可用，以获得不中断的服务。

### 本地文件与凭据

- `config.json`：供应商与行为设置；不含 API key。
- `secrets.json`：API key 与 OneBot token，仅属主可读。请勿分享。
- `data/agent.sqlite`：聊天历史、保留的想法、笔记、决策、预算、投递状态。默认历史保留 30 天，每个聊天最多 500 条消息。笔记会一直保留，直到被显式移除。
- `data/status.json`：最新运行状态，每五秒更新一次。若服务已停止，请检查 `updatedAt`。
- `src/`：应用源码；`test/`：离线测试；`scripts/`：安装与配置服务。

key 也可以通过 `LLM_API_KEY`、`DEEPSEEK_API_KEY`、`OPENAI_API_KEY`、`ANTHROPIC_API_KEY` 和 `ONEBOT_TOKEN` 提供。shell 环境变量不会被已在运行的 systemd 用户服务自动继承；本地向导是最简单的配置途径。

## 故障排查与验证

- **`waiting_for_setup`**：运行 `./agent setup`；需要一个 key 和至少一个聊天 ID。
- **QQ 断线/离线**：通过 NapCat 登录，或在 SnowLuma 中加载 QQ 进程，并启用其正向 WebSocket 服务器。检查 URL 与 token；agent 会自动重试。用 `./agent check` 验证 OneBot 端点。
- **`http_401_check_provider_config` / `http_403_check_provider_config`**：检查 key 与供应商账号。鉴权/配置类错误会退避五分钟。
- **`http_400_check_provider_config` / `http_404_check_provider_config`**：检查基址、模型与 `tokenParameter`。
- **`output_truncated_increase_maxTokens`**：调大 `provider.maxTokens`；使用能在该预算内完成结构化输出的模型/配置。
- **`invalid_json` / `invalid_ratings`**：模型返回了无效的结构化输出；不会发送消息。请使用能遵循 JSON 指令的模型。
- **`hourly_api_budget`**：已达到配置的滚动上限。随着调用滚出时间窗口，它会自行恢复。
- **没有主动回复**：低动机、冷却、静默时段或对话不活跃都可能正确地产生沉默。参见 SQLite 中的 `decisions`；沉默是设计的一部分。
- **服务以 75 退出**：另一个实例持有 `.agent.lock`。在启动服务前先停止前台进程。

运行 `./agent test` 进行本地验证。测试使用虚构的对话与本地 mock 端点，不会联系真实 QQ 接收者，也不会发起付费模型调用。只有在提供你的 key 之后，才能验证真实的 DeepSeek 鉴权。

测试覆盖范围与实况验证的局限见 [VERIFICATION.md](VERIFICATION.md)。

## 研究背景

这是一个受 [Liu et al., *Proactive Conversational Agents with Inner Thoughts*, CHI 2025](https://arxiv.org/html/2501.00383v2) 启发的实现，而不是对其实验的复现，也不声称能揭示模型隐藏的推理过程。

| 论文阶段 | 本程序 |
| --- | --- |
| 触发 | 新消息，以及在近期人类活动之后的一次停顿 |
| 检索 | 按聊天范围的历史话语与 owner 笔记，按词汇相似度与时效性排序 |
| 想法形成 | 由模型生成简短候选发言，包括快速回应与更慎重的想法 |
| 评估 | 另一次请求对动机、相关性、原创性以及支持/弃权标准打分 |
| 参与 | 轮次分配与阈值决定表达某个被选中的想法，还是将其保留 |

候选池在重启后依然存在，并会针对新上下文重新评估。开放轮次使用动机阈值；显式邀约获得优先；打断他人轮次需要更高的分数。可配置的 System 1 概率与语气控制参与风格。

有意的偏离：检索使用词汇相似度而不是 embedding；评估使用经过校验的模型数值评分，而不是按 token logprob 加权的分数。沉默乘数设有上限。额外的运行控制限制了重复、过期输出、API 用量以及静默时段内的活跃度。这些分数是模型判断，不是经过校准的概率，也不是主观感受的证据。
