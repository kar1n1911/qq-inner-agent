# QQ Inner Agent（QQ 内部思维智能体）

> **简体中文** | [English](README.md)

这是一个只服务单个 QQ 账号的常驻对话智能体，通过 NapCat 或 SnowLuma 的正向 OneBot v11 WebSocket 接入。每个启用的群聊和私聊联系人都有各自独立的上下文、记忆和候选发言池。程序默认使用 DeepSeek，同时兼容 OpenAI 的 Chat Completions 和 Anthropic 的 Messages 接口。

## 概述

- 只管理一个 QQ 账号，群聊和私聊联系人都需要显式启用。
- 首次参与群聊前先经过一段观察期，之后由模型选定初始发言风格。
- 完整的候选生成、评估、发送概率和回复预期机制。
- 群聊与个人各自隔离的长期笔记本、短期细节和特质。
- 中英文 Web 控制台，可实时调整配置、查看日志和 QQ 诊断。
- 内置 DeepSeek 预设，并支持 OpenAI/Anthropic 兼容的 API 适配器。
- 一个 Rust 运行时内核（`qq-inner-core`），Node 侧仅保留仪表盘与 CLI，通过本地控制套接字通信。

## Rust 后端

性能关键路径已用 Rust 实现（`rust/`，crate `qq-inner-core`）：OneBot v11 传输、SQLite
存储与分层记忆、决策引擎及所有逐消息策略、provider 适配。Node.js 现在只承载 Web 控制台
与 CLI，通过本地 NDJSON 控制套接字（`data/control.sock`）与 Rust 内核通信。配置、数据库
schema、`status.json` 与模型提示词 JSON 契约保持不变，因此 Rust 与 Node 内核可互换、切换可回退。

模块映射与阶段历史见 [`docs/rust-port/ARCHITECTURE.md`](docs/rust-port/ARCHITECTURE.md)，
1.0.0 发布说明见 [`CHANGELOG.md`](CHANGELOG.md)。

## 快速开始

### 环境要求

- Linux 环境，Node.js 22.13+。如果 node 不在 PATH 中，请用 `AGENT_NODE` 指定其路径。程序本身没有任何 npm 依赖。
- Python 3，仅用于 setup 和安装服务；后台常驻依赖 systemd 用户服务。
- 一个已通过 NapCat 或 SnowLuma 登录的 QQ 账号，并且开启了正向 OneBot v11 WebSocket 服务，参见[桥接连接](#桥接连接)。
- 一个 DeepSeek（或兼容服务商）的 API key，以及你要启用的群聊/私聊联系人 ID。

程序不需要任何提权操作。凭据请通过本地 setup 或控制台保存，不要写进仓库。

### 配置与启动

在终端中执行：

```bash
cd qq-inner-agent
./agent setup          # 输入 API key（终端不回显）；选择聊天 ID
./agent contacts       # 保存桥接设置后列出可选 ID；再次运行 setup 可更改选择
./agent check --api    # 校验 QQ 并发送一次小模型请求；不会发送 QQ 消息
./agent install-service
./agent status
```

用 `./agent install-service` 安装后台服务。setup 保存改动后会自动重启已安装的服务。在填入 key 和聊天 ID 之前，程序会照常尝试连接 QQ 桥，但不会调用模型，也不会发送任何 QQ 消息。启用某个聊天后，它的新消息才会交给配置好的模型服务商处理。入群观察阶段可能会抓取一段有限的群历史作为初次分析的依据，但不会把这些历史当成新消息重新处理。

所选桥必须已经登录 QQ，并且其 OneBot WebSocket 服务正在运行。这两者恢复后程序会自动重连；但程序无法替你登录 QQ，也无法修复桥本身的问题。

## 桥接连接

两种桥共用同一套正向 OneBot v11 WebSocket 适配器，同一时间只需配置其中一种。

### NapCat

1. 启动 NapCat 并登录 QQ。在 NapCat WebUI 里打开**网络配置 → 新建 → WebSocket 服务器**（正向 WebSocket）。本程序以客户端身份连接，不支持反向 WebSocket 和纯 HTTP 端点。
2. 在端口 `3001` 上启用服务，**消息格式设为 `array`**，填一个非空的 access token；两个程序跑在同一台机器上时 host 填 `127.0.0.1`。保持事件推送开启。对应的服务器条目见 [examples/napcat-websocket-server.json](examples/napcat-websocket-server.json)，把它加进 NapCat 的 `network.websocketServers` 列表并替换掉 token 占位符即可。这只是一个服务器条目，并非完整的 NapCat 配置。
3. 运行 `./agent setup`，填入 `ws://127.0.0.1:3001/`、相同的 OneBot token，以及可选的 QQ 账号 ID。账号 ID 留空（或在向导里填 `-`）表示自动识别已登录账号。也可以稍后在控制台的**配置 → NapCat / SnowLuma**里修改。记得先保存，再加载联系人。
4. 运行 `./agent check` 校验桥，运行 `./agent contacts` 列出可用 ID。选定聊天并填入模型 API key 之后，程序才会开始参与。

如果 NapCat 跑在 Docker 里、程序在本机，请在**容器内部**把 WebSocket 服务器绑定到 `0.0.0.0`，并把端口发布为 `127.0.0.1:3001:3001`，程序依旧连接 `ws://127.0.0.1:3001/`。如果桥在另一台机器上，请改用 TLS WebSocket 代理（`wss://`）或 SSH 隧道映射到本地端口；明文 `ws://` 只允许 localhost。注意端口 `3000` 通常是 HTTP，而 NapCat 的 WebUI 端口并不是 OneBot 的 WebSocket 端点。

请使用根路径 `/`，它同时承载动作和事件；NapCat 的 `/api` 路径不会推送事件。`array` 和 CQ 字符串两种消息事件都能识别，但程序发出的消息一律使用文本段。自身消息上报会被忽略。如果 NapCat 和 SnowLuma 同时运行，需要让它们使用不同端口；程序一次只对接一种桥。

兼容性依据 NapCat 的[网络文档](https://doc.napneko.icu/onebot/network)、[配置 schema](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/config/config.ts)和 [WebSocket 实现](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/network/websocket-server.ts)。自动化 mock 测试已覆盖鉴权、登录/状态、联系人、@提及、私聊回复、自身消息过滤以及两种事件格式，但尚未用真实 NapCat 账号做过端到端验证。

### SnowLuma

先登录 QQ，在 SnowLuma 中加载 QQ 进程，并启用正向 OneBot WebSocket 服务器。然后在 `./agent setup` 或**配置 → NapCat / SnowLuma**里填入它的 URL 和 access token，再运行 `./agent check`。端口以桥自身配置为准，不要假定它和 NapCat 的示例端口一致。若桥本身的 QQ 登录或组件加载出问题，本程序无法修复。

## Web 控制台

### 安装与打开

```sh
./agent install-dashboard   # 生成证书并安装/刷新用户服务
./agent dashboard-key       # 在本地显示私有登录密钥
```

用 `systemctl --user status qq-inner-dashboard.service` 查看控制台服务状态，用 `systemctl --user restart qq-inner-dashboard.service` 重启它。如果想直接在前台运行控制台，请先停掉它的服务，再执行 `./agent dashboard`。

`dashboard.json` 保存绑定地址、允许的来源（origin）和 TLS 路径。改动控制台服务端配置后需要重启控制台；而 agent 的行为设置支持热重载。密钥和配置的写入带恢复日志（recovery journal），因此即使写入两个文件的过程中被打断，控制台重启时也能回滚到一致状态。

### 访问与配置

安装好的控制台独立于 agent 运行：

- 本机：http://localhost:5097
- 局域网：`https://<主机局域网 IP>:5098`
- VPN：`https://<主机 VPN IP>:5098`

用远程设备访问时，需要先把公开的 `dashboard-ca.crt` 导入该设备的受信任根证书，再打开 HTTPS 地址。`data/dashboard-ca.key` 以及所有其他私钥都必须留在本机。证书只覆盖安装当时可用的地址，地址有变化请重新运行 `./agent install-dashboard`。能否远程连上还取决于你的局域网/VPN 路由和防火墙。HTTP 监听只绑定回环地址；对控制台端口发送明文 `http://` 请求会被重定向到同一地址的 HTTPS，因此远程设备只需要能访问 TLS 端口。

登录密钥可在本机用 `./agent dashboard-key` 查看。会话在 12 小时后过期。HTTPS、HttpOnly Cookie、CSRF 校验、来源白名单和登录限流共同保护远程访问。请不要把这个私有管理服务暴露到公网。拿到控制台密钥就能查看配置、保留的对话想法和运行日志，也能操作 agent。

在**配置**页填入 DeepSeek key，选择 API 格式和模型，并启用需要的群聊/私聊 ID。**加载 QQ 联系人**可以从已登录的账号里拉取候选项。API key 保存后不会再显示，界面只告诉你是否已经配置。改完点**保存并应用**重载 agent。配置一旦失效，正在进行的生成会被取消，但已存储的记忆不受影响。已保存的修订真正生效后，界面会给出提示。如果更换了服务商主机，必须提供新的 key，或显式清除旧 key。

**概览**页展示服务、QQ 和模型状态、就绪情况以及最近的决策。**活动与日志**页展示保留的候选发言，并每两秒刷新一次运行日志。**测试 API 连接**会用已保存的 key 发一次很小的请求，计入 API 预算，但不会发送 QQ 消息。启动、停止和重启只作用于 agent 服务，不影响控制台。

### QQ 收发诊断

概览页提供两个 QQ 诊断工具，与模型和聊天白名单无关：

- **发送自检消息**：向桥的登录接口返回的那个 QQ 账号发送一条带唯一标记的文本消息。返回成功只说明桥接受了这个动作，实际是否送达请到 QQ 的自身聊天里确认。收件人和消息内容都不可更改。发送失败或结果不确定时不会自动重试。
- **开始接收测试**：监听 60 秒。请用同一个 QQ 账号给自己或别的聊天发几条消息（文本、图片、语音、文件、回复都可以）。使用前要先在桥的 WebSocket 服务器上开启 **reportSelfMessage**；有些桥即使发送成功也不会推送自身聊天事件。查看器只在账号和发送者都与已登录账号一致时才接受 `message` 和 `message_sent` 事件。它会列出最近 30 条事件、文本预览和消息段类型，但不会下载附件、不会调用 AI，也不会把捕获内容写盘。点**停止接收**可提前结束诊断连接；开始新测试会清掉上一次的捕获。

如果一直收不到事件，请确认桥已开启自身消息上报，并且 URL 走的是 `/` 而不是 `/api`。捕获为空并不代表接收测试通过。诊断用的是已保存的连接设置，所以请先保存 URL/token 的改动；即使 agent 服务已停止，诊断依然可用。

## 配置

### 供应商与模型

向导提供 `deepseek-openai`、`deepseek-anthropic` 和 `custom` 三种选择。当前 DeepSeek 预设使用 `deepseek-flash`，你也可以换成 API 账号里可用的其他模型。两个 DeepSeek 配置档共用同一个 API key。

| 配置档 | API 基址 | 请求格式 |
| --- | --- | --- |
| DeepSeek OpenAI | `https://api.deepseek.com` | `POST /chat/completions`，bearer 鉴权 |
| DeepSeek Anthropic | `https://api.deepseek.com/anthropic` | `POST /v1/messages`，`x-api-key` 加 `anthropic-version` |
| OpenAI 兼容 | 你的基址，通常以 `/v1` 结尾 | 相对基址的 `POST /chat/completions` |
| Anthropic 兼容 | 你的基址 | 追加 `/v1/messages`；基址以 `/v1` 结尾时追加 `/messages` |

也可以直接填以 `/chat/completions` 或 `/messages` 结尾的完整端点。`provider.tokenParameter` 决定请求里用 `max_tokens`（DeepSeek 和较老的网关）还是 `max_completion_tokens`（OpenAI）。`provider.anthropicAuth` 支持 `x-api-key` 或 `bearer`；需要 workspace 的 Anthropic key 可以用 `workspaceId`。DeepSeek 预设关闭了扩展思考（extended thinking），以免拖慢这些短小的结构化阶段。程序只读取最终文本，不读取服务商的推理字段。

适配器参照 [OpenAI Chat Completions 参考](https://developers.openai.com/api/reference/python/resources/chat/subresources/completions/methods/create)、[Anthropic Messages 指南](https://platform.claude.com/docs/en/build-with-claude/working-with-messages)和 [DeepSeek API 文档](https://api-docs.deepseek.com/)。模型是否可用、网关是否支持某个参数，都由服务商决定。

在**选择模型**里，保存好服务商 URL、API 格式和 key 之后，点**加载可用模型**。可以从返回结果里挑一个 ID，也可以在**模型与 API**里手动填写，然后**保存并应用**。列出模型不会产生补全请求。列表只取服务商返回的第一页（最多 500 个 ID）；没有模型列表接口的网关、或者不在这一页里的模型，手动填即可。DeepSeek 在两种 API 格式下都用[模型列表端点](https://api-docs.deepseek.com/api/list-models/)；Anthropic 兼容服务商则用其 [Messages API 模型列表路由](https://platform.claude.com/docs/en/api/models)。

### 语言设置

控制台默认使用简体中文。页面顶部和“配置 → 语言设置”可切换 **简体中文 / English**；登录前的选择保存在当前浏览器，登录后使用已保存的界面语言。登录后点击“保存并应用”可保存界面和回复语言。回复语言可选 **跟随聊天语言、简体中文、English**，与界面语言相互独立。

候选生成、评分和最终发言的系统提示词均使用中文；切换英文界面不会把提示词改成英文。JSON 字段名、协议标识、模型 ID 和原始日志保持不变。默认角色说明也改为中文，升级时仅替换原版英文默认角色说明，自定义角色设定保持原样。

控制台默认是简体中文，也可以切到英文。界面语言和回复语言的偏好都在“配置 → 语言设置”里保存。无论界面用哪种语言，系统提示词始终是中文。回复可以跟随对话语言，也可以固定用中文或英文。已有的自定义角色和对话内容不会被翻译。

### 活跃与静默时间

在**配置 → 活跃与静默时间**里启用每日时间表，设置**活跃起始**、**静默起始**和一个 IANA 时区（例如 `Europe/Stockholm`）。活跃区间包含起始时刻、不包含结束时刻，像 22:00–06:00 这样的跨夜窗口同样支持。关掉时间表就是全天活跃；起始和结束时刻填成一样会被拒绝。在下面「连续活跃与休息节奏」关闭的情况下，处于静默期的程序会跳过收到的消息，并暂停所有自动回复（包括 @提及和私聊）。队列里的工作会在截止点被丢弃，静默时段开始后正在生成的回复也发不出去。连接和手动诊断不受影响。静默时段（quiet hours）是另一项独立限制，作用是在活跃时段内压住主动发言。

### 连续活跃与休息节奏

**配置 → 连续活跃与休息节奏**用一套概率化的可用性取代严格的每日时间表闸门，默认关闭以保持原有时间表的行为。所有聊天共用同一个账号级的活跃/休息块，@提及和私聊回复也一样。状态和到期时间都存在 SQLite 里；轮询、收到消息或重启都不会让未到期的块重新抽样。时长在配置范围内均匀抽取。相邻的块可能落在同一个状态上，所以一段连续运行可能超过单个块的最大时长。

| 设置（`agent.rhythm.*`） | 默认值 | 含义 |
| --- | --- | --- |
| `dayProbability` | 0.85 | 活跃窗口内选择活跃块的概率 |
| `edgeProbability` | 0.65 | 静默窗口两端选择活跃块的概率 |
| `centerProbability` | 0.02 | 静默窗口正中选择活跃块的概率 |
| `sigma` | 0.22 | 高斯宽度，相对于整个静默区间 |
| `activeMinSeconds` / `activeMaxSeconds` | 300 / 1200 | 活跃块持续 5–20 分钟 |
| `restMinSeconds` / `restMaxSeconds` | 600 / 2400 | 休息块持续 10–40 分钟 |

处在静默时段时，设 `x` 为按时间表本地时间在该区间内的进度（0 到 1，跨午夜时回绕）。令 `g(x) = exp(-0.5 × ((x − 0.5) / sigma)²)`，活跃概率就是 `edge − (edge − center) × (g(x) − g(0)) / (1 − g(0))`。这是一条有界的高斯形**静默**曲线：正中间最容易休息，越靠两端越可能活跃。它只是启发式规则，并非对人类行为的实测建模。这些数字是「选中某个块」的概率，不是逐条消息的发送率，也不等于活跃时间占时钟时间的比例——不同的活跃/休息时长会影响后者。

块的状态会跨每日时间表边界保留，计时按绝对经过秒数计算。时区和夏令时变化只影响下次抽样所用的本地时间曲线。长时间离线后恢复时，程序只抽一个新块，不会补算错过的那段时间。改动节奏或时间表设置会开启新块，改动无关设置则保留当前块。关掉每日时间表后全天都用 `dayProbability`；关掉节奏则回到原来的严格时间表。

休息期间会跳过收到的消息并丢弃排队的回复；如果某次回复的生成跨越了块边界，即使下一个块是活跃的，这条回复也不会发出。重新活跃不会触发问候，也不会补发错过的消息。活跃状态下，观察期、静默时段、预测、逐条发送概率、冷却和预算依然生效，所以静默时段可能压住随机活跃的夜间块里的主动消息。概览页会显示当前状态、下次抽样时间、抽到的概率和当前曲线概率。这一切不需要额外的模型请求。

### 参与限制与热更新

可以直接在控制台里保存并应用，也可以本地编辑 `config.json`。程序每秒检查一次改动，配置写错时继续沿用上一份。[`config.example.json`](config.example.json) 是一份起步配置；完整默认值和校验规则见 [`src/config.mjs`](src/config.mjs)。

| 设置 | 默认值 | 作用 |
| --- | --- | --- |
| `agent.proactive` | `true` | 在已启用的聊天里考虑非受邀发言 |
| `agent.threshold` | `4.09` / 5 | 开放轮次所需的动机分数 |
| `agent.interruptThreshold` | `4.8` / 5 | 话题正指向他人时所需的动机分数 |
| `agent.system1Probability` | `0` | 可选：低动机简短回应的触发概率 |
| `agent.proactiveCooldownSeconds` | `180` | 两次主动发言之间的最短间隔 |
| `agent.maxProactivePerHour` | `6` | 每个聊天的主动发言上限 |
| `agent.maxMessagesPerHour` | `30` | 每个聊天的总输出上限（含回复） |
| `agent.pauseSeconds` | `45` | 人类发言后触发停顿的秒数 |
| `agent.activeWindowSeconds` | `900` | 超过这个窗口就不再唤醒已冷掉的聊天 |
| `agent.quietHours` | `23:00–08:00`，Europe/Stockholm | 压住非受邀发言；填 `null` 关闭 |
| `agent.dryRun` | `false` | 只评估和记录决策，不实际发送 |
| `provider.requestsPerHour` | `120` | 全局滚动 API 调用上限（含重试） |

已启用私聊里的直接消息、显式的 QQ @提及，以及跟在别名后的 `:`/`：`，都会把内容指向 agent。直接回复会绕过主动发言冷却和静默时段，但仍受总消息/API 预算约束。由模型推断出的邀约无法绕过这些保护。其他机器人账号可以写进 `agent.ignoredUsers`。

## 对话行为

### 入群观察期

白名单里的群默认开启观察期，升级前就启用的群也包括在内。观察期从程序首次登记该群时开始；收到自身账号新的 `group_increase` 入群通知后会重新开始，重复的通知不会重复触发。状态和选定的风格在程序重启后仍然保留。私聊不受这道限制。

群里的第一次回复（包括被 @）之前，默认要同时满足**经过 300 秒**和**累计 20 条不重复的人类新消息**。可以在**配置 → 入群观察期**里改这两个阈值、改成满足其一，或者直接关掉观察。时间是从登记那一刻起的墙上时钟；收到哪些消息仍然由既有的活跃时间表决定。历史样本、自己的回声、重放事件、被忽略用户和无关聊天都不计入。如果群里一直没人说话，观察期可能无限期等下去。越过阈值并不会强制打招呼，正常的活跃窗口和发送策略依旧生效。

程序会通过当前 OneBot 连接请求 `get_group_info`、`_get_group_notice` 和 `get_group_msg_history`。这些接口列在 [NapCat 的 API 兼容文档](https://doc.napneko.icu/develop/api)中，其他桥未必实现这些扩展端点。采集器对群信息、最多五条文本公告和一段可配置的历史样本（默认 30 条）都做了上限。不支持、失败或格式有误的来源会被记为不可用，而不会编造内容；实时的聊天记录仍然可以支撑一个保守的初始风格。图片和文件 URL 不会被抓取。历史样本只用于分析，不会重放进发送流程，也不计入阈值。采集到的历史和公告会在配置的原始数据保留期后删除，但选定的风格会保留。

一旦越过阈值，程序会单独发一次中文 `ORIENT` 请求，分析拿到的群上下文，选出一个初始发言风格、一段简短概述和几个话题。这次调用走既有的服务商和 API 预算。输出无效或服务商报错时闸门继续保持关闭，60 秒后重试。必须先分析成功，才会进入想法形成、评估和表达；这些阶段都会把选定的风格作为参考。每次成功的初次定向会多一个模型请求，失败的尝试也会计入；之后的对话学习还能继续改进风格。群信息和公告始终是**不可信的引用内容**。

**活动与日志 → 入群观察期**会显示已过时间、消息计数、各来源是否可用以及选定的风格。元数据采集从第一个符合条件的群处理周期开始。自动化验证期间没有真正抓取过 QQ 历史，也没有跑过模型分析。

### 发送策略与预测

在**配置 → 发送策略与预测**里可以调整这套发送检查，它默认开启。既有的时间表、静默时段、冷却和速率限制都照常生效。选中的候选在表达之前会先经过一次中文 `FORECAST` 请求：判断该不该发、正常回复/沉默/负面反应各自的概率，并给出一段简短的回复计划。预测无效时按保守处理（fail closed）。这会给符合条件的周期多加一次模型请求（走完一整轮共四次），并计入既有的 API 预算。

主动发言的准入概率由下面这些因子相乘得到：

- 基础概率（默认 0.8）。
- 沉淀因子：`min(1, 距最近一条人类消息的秒数 / 15)`。
- 恢复因子：`min(1, 距上次被策略计入的投递尝试的秒数 / 300)`，没有则为 1。
- 节奏因子：`1 / (1 + 最近一分钟人类消息数 / 6)`。
- 动机因子：`0.25 + 0.75 × (调整后分数 − 1) / 4`。
- 预测因子：`1 − 预测的负面反应概率`。

时间除数、节奏除数和基础概率都可以配置。抽样在预测请求之前完成，所以模型延迟不会把发言概率抬高。直接请求用自己独立的基础概率（默认 1），不经过上面这些折减。只要预测建议再等等，或负面反应概率超过配置上限（默认 0.4），两种模式都会被否决。每条触发的人类消息只抽一次并持久化：被拒绝的尝试不会因为沉默计时器或重启而重新抽。关掉这项检查就回到原来的选择流程。

表达时会参考回复计划。只有在确认发送之后才建立一条预期，默认按聊天保留 300 秒。下一轮会拿到那条预测，外加过了多久、期间是否有新的人类消息；但对方发了消息并不等于回复或同意。预期不会安排自动追问。**活动与日志 → 发送预测**会显示概率、抽样结果、各计时因子、结果预测、计划和投递状态。这些预测是主观估计，既不是校准过的概率，也不是对论文实验的复现。

### 自适应角色与记忆

默认中文角色现在更看重接住话题、做点轻松的联想和幽默，并抛出相关且好回答的话头，而不是没完没了地提问或硬找存在感。和旧版完全一致的默认角色会自动迁移，自定义角色原样保留。

实际使用的提示词由你可编辑的角色设定，加上按范围划分的笔记本和特质拼成。键是 `(chat, subject, layer, topic)`：群聊里的 subject 是 `group` 和 `person:QQ_ID`，私聊里只允许该联系人的 `person:QQ_ID`。同一个人在两个群、以及在私聊里的记录彼此独立。只有当前群和最近一位人类发言者的笔记本会进入生成；群共享的短期上下文仍会带上其他成员的署名消息，但不能把它们和当前发言者的特质混在一起。保留的候选想法也按发言者分开存放，避免个人上下文经由这个缓存泄漏。

| 层 | 内容与更新方式 | 每个 subject 的默认上限 |
| --- | --- | --- |
| 长期笔记本 | 以话题为键，记录过往事件、约定和进行中的话题。不动的话题保留，已有键可覆盖修订，过时的话题显式遗忘。 | 1,800 字符，最多 24 个话题，更新后保留 365 天 |
| 短期细节 | 带署名的原始人类消息，自动记录，不调用模型。群视图和个人视图在检索时去重。 | 40 条，每条 1,000 字符，保留 72 小时 |
| 特质 | 稳定的兴趣、表达习惯、互动风格和群里的话题偏好。与事件历史分开更新。 | 900 字符，最多 24 个话题，更新后保留 180 天 |

长期存储借用了 [Mamba 的选择性状态空间](https://arxiv.org/abs/2312.00752)里「随输入筛选、保留循环状态」的思路，但这里只是一个有界的应用层笔记本，**不是 Mamba 神经网络，也不是对其 SSM 的数学复现**。模型在 `FORM` 里最多提出四个话题补丁，没被改到的话题原样保留。容量吃紧时，重要性高的条目优先留下，最近更新过的条目在并列时胜出。修订记录、来源 ID、作者和时间戳都可以查看。长期笔记本和特质的过期独立于原始聊天日志的保留期，所有状态都存在 SQLite 里。默认每个聊天最多保留 200 个人，满了之后淘汰最久没更新的个人范围。

**配置 → 自适应角色与记忆**控制这些上限和学习节奏（默认：8 条新人类消息且间隔 300 秒）。同一次 `FORM` 调用分析当前群和当前发言者，不会为每个过去的成员单独反思一遍。个人更新只能引用该人在当前聊天里的真实消息；群更新要求至少有两位不同成员的消息。这里校验的是署名归属，不是事实真伪或共识。提示词明确要求保留分歧，绝不因为一个人就推断整个群的偏好。作者、范围、层、来源有误或补丁格式不对，整批更新都会被拒绝。这个过程不需要额外的 API 请求，只是结构化输出会多花些 token。

当前群和当前发言者的笔记本与特质会被直接送入提示词，所以过往上下文不依赖关键词命中。短期 RAG 用最近三条人类消息，按词汇重叠（包含中文字符对）、时效性和 owner 笔记偏好，对允许范围内的细节以及最多 50 条 owner 笔记排序，默认返回最多 6 条相关细节，并排除已经在提示历史里的消息。每个阶段都会带上 subject、时间和来源信息。它不需要 embedding 接口或向量数据库；代价是关键词检索可能漏掉换了个说法的内容。

**活动与日志 → 学到的聊天风格与记忆**最多列出 200 条，笔记本和特质排在前面，并按聊天、subject 和层分开。重置只清掉该 subject 的三层，原始聊天历史和其他 subject 不受影响，进行中的学习会作废，之后新消息还能重新教它。关闭学习会停止三层的采集、更新和使用，但当前对话上下文和 owner 笔记仍然可用。调低上限会在热重载时生效；调长保留期只影响之后的更新，不会把已过期的数据救回来。

升级说明：之前未分范围的 `learned_memories` 和 `chat_learning.style` 会作为遗留记录留在本地，但不会进入这条新管线，也不会自动归属给某个人或某个群。旧的 `learning.maxMemories` 和 `learning.memoryDays` 仍为兼容而接受；新的分层上限改用 `agent.memory.*`。发送概率、冷却、静默时段和活跃时间表继续生效。

### 请求流程与能力边界

一轮通常这样消耗 API 请求：候选选择弃权时两次；发送预测或概率检查弃权时三次；真的发送时四次。关掉发送策略就不再有预测请求。突发消息会被合并，最多两个聊天并发。生成过程中如果来了新消息，旧回复会被丢弃，改为处理最新上下文。投递结果不确定时会记录下来，绝不自动重发——宁可偶尔漏发，也不重复发帖。

支持文本和 @提及。图片、音频、文件和转发消息的内容只用附件标记表示，不会下载或解读。程序没有 shell、浏览器、文件访问等任何操作工具，能聊天，但不能执行通用任务。

## 运行与本地数据

### 日常命令

| 命令 | 用途 |
| --- | --- |
| `./agent setup` | 配置服务商、key、聊天范围、名称、角色和预览模式 |
| `./agent contacts` | 在本地列出可用的群和好友 ID |
| `./agent status` | 查看服务状态和最近的连接情况 |
| `./agent logs` | 跟踪运行日志；不含消息正文和 API key |
| `./agent stop` | 停止自动参与 |
| `./agent restart` | 重载配置并重启 |
| `./agent start` | 在前台运行；有实例在跑时会拒绝启动 |
| `./agent check --api` | 鉴权并发一次小模型测试请求 |
| `./agent test` | 用本地 mock 服务商和 OneBot 跑离线测试 |
| `./agent add-memory group:123 "The club meets on Sundays."` | 为指定的那个聊天加一条 owner 笔记 |

私聊记忆用 `private:123`，而不是 `group:123`。只有被选中的聊天会被处理；要加更多聊天，重新跑 setup 或改 `config.json` 后重启即可。setup 里输入 `-` 可以清空列表。移除某个聊天后它就不再被处理，已存的本地历史会留到保留期结束。

`qq-inner-agent.service` 用户服务会在崩溃后自动重启。WebSocket 心跳每 30 秒探一次 QQ，连接失败时按指数退避加抖动重试。HTTP 请求复用连接池、带超时，并对瞬时故障重试。对话状态存在本地，不依赖模型服务端记住会话。程序不会发付费的保活请求。

`loginctl show-user "$USER" -p Linger` 可以看用户服务能否在注销后继续运行，需要时用 `loginctl enable-linger "$USER"` 打开。但这不会让桌面 QQ 会话在注销或挂起后活着——想不中断地跑下去，请让机器保持唤醒，并让 QQ/SnowLuma 一直可用。

### 本地文件与凭据

- `config.json`：服务商和行为设置，不含 API key。
- `secrets.json`：API key 和 OneBot token，仅属主可读，请勿分享。
- `data/agent.sqlite`：聊天历史、保留的想法、笔记、决策、预算和投递状态。历史默认保留 30 天，每个聊天最多 500 条消息；笔记会一直留着，直到被显式删除。
- `data/status.json`：最新运行状态，每五秒更新一次。服务停了的话可以看 `updatedAt`。
- `src/`：程序源码；`test/`：离线测试；`scripts/`：安装和配置脚本。

key 也可以通过 `LLM_API_KEY`、`DEEPSEEK_API_KEY`、`OPENAI_API_KEY`、`ANTHROPIC_API_KEY` 和 `ONEBOT_TOKEN` 提供。注意已经在跑的 systemd 用户服务不会自动继承 shell 环境变量，所以本地向导是最省事的配置方式。

## 故障排查与验证

- **`waiting_for_setup`**：跑一下 `./agent setup`；需要一个 key 和至少一个聊天 ID。
- **QQ 断线/离线**：通过 NapCat 登录，或在 SnowLuma 中加载 QQ 进程，并开启其正向 WebSocket 服务器。检查 URL 和 token；程序会自动重试。用 `./agent check` 验证 OneBot 端点。
- **`http_401_check_provider_config` / `http_403_check_provider_config`**：检查 key 和服务商账号。鉴权或配置类错误会退避五分钟。
- **`http_400_check_provider_config` / `http_404_check_provider_config`**：检查基址、模型和 `tokenParameter`。
- **`output_truncated_increase_maxTokens`**：把 `provider.maxTokens` 调大；选一个能在该预算内写完结构化输出的模型或配置。
- **`invalid_json` / `invalid_ratings`**：模型返回的结构化输出不合法，消息不会发出。换一个能遵循 JSON 指令的模型。
- **`hourly_api_budget`**：到达了配置的滚动上限，等调用滚出时间窗口就会自行恢复。
- **没有主动回复**：动机分数低、冷却中、处于静默时段或对话已冷下来，都可能正确地保持沉默。可以看 SQLite 里的 `decisions`；沉默本来就是设计的一部分。
- **服务以 75 退出**：`.agent.lock` 被另一个实例占用。先把前台进程停掉，再启动服务。

本地验证跑 `./agent test`。测试用的是虚构对话和本地 mock 端点，不会联系真实 QQ 接收者，也不会发起付费调用。真实的 DeepSeek 鉴权只有在你填好 key 之后才能验证。

测试覆盖范围和实况验证的局限见 [VERIFICATION.md](VERIFICATION.md)。

## 研究背景

这是一个受 [Liu et al., *Proactive Conversational Agents with Inner Thoughts*, CHI 2025](https://arxiv.org/html/2501.00383v2) 启发的实现，不是对论文实验的复现，也不声称能揭示模型隐藏的推理过程。

| 论文阶段 | 本程序的对应做法 |
| --- | --- |
| 触发 | 新消息，以及近期人类活动之后的一次停顿 |
| 检索 | 聊天范围内的历史话语和 owner 笔记，按词汇相似度和时效性排序 |
| 想法形成 | 由模型生成简短的候选发言，既包括快速回应，也包括更慎重的想法 |
| 评估 | 另外发一次请求，对动机、相关性、原创性以及支持/弃权标准打分 |
| 参与 | 由轮次分配和阈值决定是说出某个选中的想法，还是先留着 |

候选池在重启后依然存在，并会针对新上下文重新评估。开放轮次看动机阈值；被明确点名时优先；要打断别人的话轮则需要更高分数。System 1 概率和语气都可配置，用来调节参与风格。

几处有意的偏离：检索用词汇相似度而不是 embedding；评估用经过校验的模型数值评分，而不是按 token logprob 加权的分数。沉默乘数设了上限。另外还加了一些运行层面的控制，用来约束重复、过期输出、API 用量和静默时段内的活跃度。这些分数都是模型判断，不是校准过的概率，也不能当作主观感受的证据。
