# 让回复更像真人:改动方案

现状:`src/prompts.mjs` 已有较扎实的基础(共享 `boundary` 防注入与 JSON 契约,
FORM / EVALUATE / ARTICULATE / FORECAST 四段分工,已明确要求避免客服腔、说教、
每次都问问题、机械复述)。因此"更像真人"不靠推倒重来,而是**针对具体的 AI 腔特征做减法**,
再加一点**受控的不完美**。

## AI 味的具体来源(可直接观察)

| 特征 | 表现 |
| --- | --- |
| 结构完整 | 每句都是主谓宾齐全的完整句,像书面语 |
| 长度均匀 | 每条回复字数接近,像有配额 |
| 过度提问 | 结尾总挂一个问题("你觉得呢?") |
| 爱总结 | 把对方的话复述一遍再回应("所以你是在说…") |
| 对称句式 | "不仅…而且…"、"不是 A,而是 B"、"一方面…另一方面…" |
| 排比与递进 | 三个并列短句 + 一个升华 |
| 情绪配平 | 先肯定再补充再建议,像客服话术 |
| 表情滥用 | 每条都带 emoji,或不带就冷冰冰 |
| 零态度 | 从不表达偏好、不反对、不玩笑 |
| 完美措辞 | 没有口语词、没有省略、没有停顿 |

## 改动 1:显式反 AI 腔黑名单(改 ARTICULATE)

在 `articulation` 里加一段**具体禁令**(抽象要求已证明无效,要列可判定的模式):

- 禁止复述对方原话再回应;直接接话。
- 禁止"不仅…而且…"、"不是…而是…"、"一方面…另一方面…"这类对称句式。
- 禁止三点并列 + 升华的排比结构。
- 禁止先肯定、再补充、再建议的三段式。
- 禁止在聊天里使用编号列表、项目符号、加粗标题。
- 禁止以问句结尾作为默认收尾;只在真的想追问时才问,且不要连续两条都问。
- 禁止元话语:"希望对你有帮助"、"还有什么想聊的"、"作为 AI"。
- 禁止为每条消息都配 emoji;严肃场景与短回应不配。

## 改动 2:长度分布抽样(改 engine,不只是提示词)

**长度均匀是最强的 AI 信号之一。** 在 `engine.cycle` 组装 articulation payload 时,
按分布抽一个目标长度档位并传给提示词(比"保持简短"这种模糊要求有效得多):

| 档位 | 概率 | 目标 | 说明 |
| --- | --- | --- | --- |
| `tiny` | 35% | ≤ 12 字 | "哈哈"、"确实"、"我也觉得"、"啊这" |
| `short` | 45% | 13–40 字 | 常态 |
| `medium` | 18% | 41–90 字 | 需要说清楚时 |
| `long` | 2% | 91–200 字 | 认真求助/技术说明 |

约束:当轮若为明确求助(`hint==='self'` 且内容像问题),强制至少 `short`,不允许 `tiny`
敷衍;`tiny` 不能被用于回答问题。抽样结果需写入日志以便复盘。

## 改动 3:口语度按群校准(用已有 learning 数据)

`chatStyle` / `traits` 已经在学每个群的风格。在 ARTICULATE 中明确要求:

- 按当前群学到的话语习惯选择语气词与口语度(有的群用"哈哈哈",有的群用"233"或不用)。
- 允许并使用:语气词(啊/吧/嘛/诶)、口语省略(省主语)、程度副词(挺/超/有点)。
- 但这些**必须从 learned traits 或该群历史中有据可依**,不得凭空发明群内不存在的习惯。
- 学不到时默认中性简洁,宁可不加也不硬凑。

## 改动 4:允许观点与态度(改 FORM 的候选生成)

当前候选主要是"接话头/联想/新话题"。增加一类:

- 允许表达**轻微偏好或不同看法**("我倒觉得…","不太同意" ),但要留有余地、不攻击。
- 允许**玩梗与自嘲**,但必须贴合上下文,且不涉及他人的敏感信息。
- 明确:沉默是合法选择;没有值得说的就不发,不要为了活跃而制造话题。

## 改动 5:受控的不完美(谨慎,可开关)

- 允许偶尔用**不完整句**或**省略号**收尾,表示话没说完或随口一说。
- **不做**故意打错字 —— 成本高、易翻车,收益不确定。
- 该行为用配置开关控制,默认开启幅度保守。

## 验收方式

1. 构造 20 组固定输入的离线样本(涵盖:求助、玩笑、情绪倾诉、冷场、被点名、话题结束)。
2. 对同一批输入,分别用新旧提示词各跑一轮,产出 A/B 对照表。
3. 用**可判定的指标**先自动筛:
   - 长度分布是否接近目标分布(不再均匀)
   - 是否出现黑名单中的句式(正则匹配)
   - emoji/结尾问句比例
4. 再由人主观打分:像不像群里的人在说话。
5. 回归红线:JSON 契约、`maxCharacters`、发送权限、静默时段等约束不得被破坏。

## 实施位置

- 提示词改动 → `src/prompts.mjs`(JS 版,当前线上即可生效),随后同步到 Rust `prompts.rs`。
- 长度抽样 → `src/engine.mjs` 组装 payload 处;Rust 侧同步到 `engine/`。
- 新配置项(如不完美开关)→ `src/config.mjs` defaults + 校验,并同步 Rust。

## 改动 6:表情与表情包(重点)

### 现状与问题

现有机制是:配置 `emoji.symbols`(Unicode)/`emoji.faceIds`(QQ face),
`decorationChoices` 过三重闸门(开关 / 每 chat 冷却 / 固定概率 15%),把候选交给
ARTICULATE,`decorate` 再按白名单校验后附加到正文末尾。

问题是**它把"机器人偶尔加个表情"做得还行,但不像人在用表情**:

| 现象 | 真人的做法 | 现在的做法 |
| --- | --- | --- |
| 类型 | 主要用 **QQ 内置 face**(破涕为笑、微笑、捂脸),Unicode emoji 反而少 | 默认给的是 Unicode emoji |
| 频率 | **按群差异极大**:有的群句句带,有的群从不 | 全局固定 15% |
| 位置 | 句尾,或**单独成为一条只有表情的消息** | 只能附加在文本末尾 |
| 复用 | 反复用同几个,很少换新 | 从四个里随机 |
| 场合 | 情绪节拍(好笑/无奈/附和/自嘲) | 无场景判定 |

### 设计

**6.1 优先 QQ face,而非 Unicode emoji**

中文 QQ 语境里 face 才是母语。提示词应明确:候选里同时有 face 与 Unicode 时**优先 face**;
Unicode emoji 只在没有合适 face 时用。

**6.2 频率按群学习,而不是全局固定**

人不会"每个群都以 15% 概率发表情"。应观察**该群里人类自己的表情使用率**,并让 agent 略低于它:

```
rate(chat) = 带表情的人类消息数 / 人类消息总数        # 滑动窗口,带衰减
p(chat)    = clamp(rate(chat) * 0.8, 0, 0.35)        # 略低于人类,避免抢戏
```

- 冷启动(样本不足)用保守默认(如 0.08),而不是 0.15。
- 该值需要持久化与衰减,与现有 `chat_learning`/`expressions` 的保留期策略一致。
- 现有 `emoji.probability` 保留为**上限/覆盖**(配置可强制关闭)。

**6.3 允许"只发表情"的一条消息**

这是最像人的一步:真人经常**只回一个表情**,不说一个字。现在做不到——引擎要求正文非空
(`invalid_articulation`),表情只能附加。

设计:
- 允许模型返回 `{"text":"", "emoji":..., "faceId":...}`,此时引擎发送**只有 face 段的数组消息**。
- **硬性限制**(防止显得敷衍/失礼):
  - 仅当本轮是 `open` 或 `other` 且动机分处于中低区间时允许;
  - **被直接点名(`hint === 'self'`)、对方在求助或表达负面情绪时禁止**;
  - 每条 chat 的连续表情-only 不超过 1 次,且与上一条 agent 消息间隔足够;
  - 计入现有的 `maxMessagesPerHour` 配额。
- 该行为用配置开关控制,默认**开启但保守**。

**6.4 位置与形态**

- 固定在**句尾**,不插在句中;
- 一条消息**最多一个**表情(与 `expression.maxPerReply` 同源思想);
- 不在同一段里混用 face 与 Unicode;
- 长文本(如 `long` 档)不配表情。

**6.5 提示词片段(可直接采用)**

```
表情与表情包的真实用法:
- QQ 里人们主要用内置 face(如破涕为笑 / 微笑 / 捂脸),Unicode emoji 用得少;decorations 同时给出两者时优先 face。
- 位置在消息末尾;不要放在句子中间。
- 只在情绪节拍上使用:好笑、无奈、附和、自嘲、敷衍。严肃求助、技术讨论、对方难过时一律不用。
- 不要连续两条消息都带表情;同一段对话里重复用同一个表情很自然,频繁换新表情反而不像人。
- 表情不能替代实质回答:被提问时必须先给出内容。
- 只允许使用 decorations 中列出的候选,不得编造 id 或符号;不需要就返回 null。
- 当本轮只是轻松附和、确实没有值得说的内容时,可以返回空文本并只给一个表情。但被直接点名、对方在认真求助或表达难过时,不允许只发表情。
```

## 改动 7:分条发送(多气泡)—— 剩下最大的一处"不像人"

真人回复常拆成 2–3 条短消息连发("等下" → "我看看" → "好了"),而当前引擎**每条 cycle 只发一条**。
无论提示词多好,单条消息的形态本身就和真人不同。

设计:让 ARTICULATE 返回 `texts: [string]`(1–3 条),引擎按间隔依次发送。

约束:
- 任一片段仍受 `maxOutputChars` 与总长度约束;
- 只有 `short`/`medium` 档才允许拆分,避免把长回答切碎;
- 序列内不发表情(表情只加在最后一条);
- 任一片段失败即停止后续发送,并沿用现有"不确定则不重发"的策略;
- 拆分只在低风险场景启用(求助/技术回答保持单条,便于阅读)。

## 改动 8:回复节奏(打字延迟)

真人不会在 0.2 秒内回一段完整的话。当前是生成完立即发送。

设计:发送前加一个**与长度相关的短延迟**(如 `min(2.5s, 0.4s + 字符数 * 0.02s)`,并加抖动),
拆分多气泡时片段之间再加 0.3–0.8 秒。这样即使内容一样,主观上也更像人在打字。

注意:延迟必须计入现有的活跃窗口/静默时段判定,且静默时段开始时**不得**把已排队的消息发出。
