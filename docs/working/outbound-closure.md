# 出站闭环：实测结论（2026-10-14）

**目的**：确定出站确认（T / ★ 的残留缺口）到底有哪些证据路径可用。
**方法**：在 VM 上对二人群 `1127261371` 做了受控实测（agent 处于「停止参与」，
测试消息由 HTTP API 直发，绕过 agent）。

---

## 一、三条证据路径的实测结果

| 方案 | 可用性 | 证据 | 约束 |
| --- | --- | --- | --- |
| **A. 接收 `message_sent`** | ✅ **可用** | 直连 `ws://127.0.0.1:3001/` 抓帧：发送后 **1787 ms** 收到 `post_type="message_sent"`，**`message_id` 与 ACK 完全一致** | 需实现接收（当前被丢弃） |
| **C. `get_msg` 读回** | ✅ 可用 | 我发的消息读回成功，`time` 正确 | ⚠️ **只能查近期** —— 两天前的 `message_id` 返回 `retcode 200 "消息不存在"` |
| **B. ACK 终态** | ✅ 永远可用 | `retcode: 0` + `message_id` | 无独立收件端确认，但**绝不误报** |

**A 的帧样本**：
```json
{"self_id":3879337324,"user_id":3879337324,"time":1792000010,
 "message_id":362736398,"sender":{"user_id":3879337324,"nickname":"Kar1n1911"},
 "raw_message":"WS-SELFTEST-...","post_type":"message_sent",
 "message_sent_type":"self","group_id":1127261371}
```

## 二、时间来源：**已证明来自消息原始时间，不是兜底**

**曾担心**（Agent 1 提出）：NapCat 把 `msgTime` 转成 OneBot `time`，
**缺失时会回落到本机 `Date.now()`**。

**实测否定了这个担心**（两条独立证据）：

| 证据 | 内容 |
| --- | --- |
| **旧日志对照** | 10-12 的日志里，`"msgTime":"1791793608"` 与 `"time":1791793608` **逐条相等**；而 `1791793608` 换算为 UTC 正好是 10-12 当天（与日志时间戳吻合） |
| **两天前的消息** | 若 `time` 是 `Date.now()` 兜底，两天前消息也会显示"现在"；**实际显示的是两天前** |

**结论**：
- `time` = QQ 原始 `msgTime` **直接透传**；
- **只要 `msgTime` 存在，就是消息的原始时间**；
- 兜底只在 `msgTime` 缺失时发生 —— **实测中未观察到缺失**。

## 三、之前收不到自回显的根因：**是我们的代码丢弃了它**

```
NapCat 确实发出了 message_sent  ✅（抓帧证实）
        ↓
agent 的 onebot 适配器：对 message_sent 报「未实现」
agent 的 policy：在入口跳过 self_message
        ↓
事件被丢弃 → 日志里看不到
```

**这解释了"开了 `reportSelfMessage` 仍没有对账"** ——
**不是 NapCat 不发，而是我们没接**。

**注**：NapCat 侧配置本来就是对的（`正向WS enable=True`、`reportSelfMessage=True`）。

## 四、推荐的实现形态

```
发送 → ACK（retcode + message_id）           ← B，永远可用，基线
     → 等 message_sent（≈1.8s，按 message_id 匹配）  ← A，实时加速
     → 超时 → get_msg 读回（仅近期）          ← C，兜底
     → 全部失败 → 保持 sent_unconfirmed        ← 绝不伪造
```

**不变量**：
1. **只有匹配的二次证据**才允许把状态升级为确认；
2. **不得伪造服务器时间**；
3. **不得因查询失败自动重发**；
4. **未确认就是未确认** —— 不因为"看起来成功了"而改状态。

**关于 C 的窗口约束**：由于旧消息查不到，
**"定期批量对账"不可行** —— 只能**发送后即时对账**。
若 A 不可用且 C 已过期，状态就**永久停在 `sent_unconfirmed`**（这是诚实的）。

## 五、尚未验证的部分

| 项 | 状态 |
| --- | --- |
| A 在**群聊之外**（私聊 / 频道）是否同样上报 | ❓ 未测 |
| A 的**丢失条件**（agent 离线、事件积压） | ❓ 未测 —— 实现时必须考虑超时兜底 |
| C 的窗口到底多长 | ❓ 只知道 > 数小时且 < 2 天 |
| **同一 `message_id` 的幂等升级** | ❓ 未测（实现时需要保证重复事件不重复记账） |

**这些不是"待办"，而是实现时必须按"证据可能缺失"来设计的理由。**
