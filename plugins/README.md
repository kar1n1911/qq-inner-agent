# Plugin manifests and deployment list

The seven package directories contain Rust adapters compiled through `rust/src/engine/io/adapters/mod.rs`. Their `manifest.json` files describe those adapters; reading a manifest does not execute code or grant permissions. `plugins.json` is the deployment request. It uses schema version 1 and `mode: "auto"` so every first-level package directory appears in discovery. Every listed instance starts with `enabled: false`: discovery alone never activates a plugin.

Each manifest uses `version: "0.1.0"` as an initial manifest/package version. None of these seven plugins has been independently released; this is not the repository's `1.2.0` version or a claim of independent release maturity. All declare `hot_reload: false`, since this deployment cannot guarantee hot replacement. `host_permissions` records requested or actual network/file access; it is not an enforcement gate. In particular, A_memorix dials gRPC directly today, so its gRPC declaration does not imply host-mediated access control. Values such as `configured:base_url` and `configured:card_root` describe the origin or root supplied at deployment time, not wildcard grants.

`status: "skeleton"` means a package is structurally recognized but cannot be enabled. Discovery returns `state: "skeleton"` and `reason: "plugin_is_skeleton"`. The Rust preflight keeps disabled skeleton entries visible and rejects any enabled skeleton before loading. The older `status: "placeholder"` and literal `TBD` rejection rules remain in force.

| Package | State | Basis |
| --- | --- | --- |
| `onebot` | Available | Built-in chat adapter has inbound mapping and send/recall operations; advertised capabilities are `mention` and `reply`. `media` remains unsupported. Requires host OneBot callbacks when enabled. |
| `a_memorix` | Available after service probe | Remote gRPC adapter implements upsert, forget, retrieve and probes namespace capabilities. Factory requires a successful probe with `text_retrieval`. Other memory abilities remain dynamic. |
| `openai` | Available with endpoint and credentials | Built-in HTTP adapter connects to a configured remote service. Advertises text completion, streaming, model listing, truncation signal and JSON mode. |
| `claude` | Available with endpoint and credentials | Same HTTP adapter with Claude request shape. JSON mode is unsupported. |
| `sillytavern` | Available with card root and bindings | Built-in persona card loader supports V1/V2, PNG chara and character book parsing. V3 and character book injection are unsupported. |
| `ollama` | Skeleton | The HTTP adapter is compiled into the core and connects to a local Ollama service, so its topology is `InProcess` for this package. The current factory instead requires `Sidecar` plus a managed executable. No such executable exists here. Enabling honestly requires a future factory change, which this task does not make. |
| `null` | Skeleton | The single adapter implements six port kinds, while a manifest represents one kind. Its `kind: "Multiple"` is accepted only for skeleton discovery. All six ports return explicit failures. Splitting it into six installable packages would require separate packaging and factory support. |

`ollama` remains in `plugins.json` as a disabled skeleton entry so its limitation is visible in deployment status. `null` is discovered as a skeleton but is omitted from the deployment list: one instance could not truthfully select one of its six kinds. Both remain impossible to activate; explicitly adding either with `enabled: true` fails preflight. `Remote` on the model and memory packages describes the service they contact; the Rust adapter itself is compiled into the core. The `entry` fields identify either the built-in adapter or the configured endpoint. HTTP and gRPC protocol metadata describes the upstream service, not a separately implemented host/plugin wire protocol.

`plugins.json` does not create a dynamic Rust loader. Activation still goes through the trusted factory. The current factory performs additional configuration, endpoint, capability and host checks; a manifest that passes discovery is not proof that activation will succeed. In particular, `a_memorix` requires a reachable compatible gRPC service and `onebot` requires the host callbacks. The skeleton state is a package constraint, separate from an ordinary disabled request.
